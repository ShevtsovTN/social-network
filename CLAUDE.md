# Social Network: учебный монолит

## Цель
Скелет социальной сети: регистрация, логин, просмотр анкеты по ID, поиск анкет по префиксу имени и фамилии.
Эндпоинты: `POST /login`, `POST /user/register`, `GET /user/get/{id}`, `GET /user/search`.
Контракт описан в `docs/openapi.json` и является источником истины.

## Архитектура
- `packages/core`: общий composer-пакет, только бизнес-логика
  (Domain и Application, включая интерфейсы портов). Никакой инфраструктуры.
- `apps/native`: чистый PHP. Свои Infrastructure и Presentation, свой composition root.
- `apps/symfony`: Symfony. Свои Infrastructure и Presentation, своя конфигурация DI.
- `frontend/`: статический UI (HTML + ES-модули, без сборки) для ручной проверки API.
  Ходит в оба приложения через `nginx-frontend` (dev-only), контракт не меняет.
- Подключения к БД: запись и логин идут на primary (`DB_HOST`), `get` и `search` на реплики через HAProxy (`DB_READ_HOST`).
- `social-network-docker/`: Dockerfile'ы и конфиги php-fpm, nginx, postgres.
  `docker-compose.yaml` и `.env` лежат в корне репозитория.
- `db/migrations/`: общая SQL-схема для обоих приложений.
- `db/seed/`: генерация миллиона анкет из `people.v2.csv` (`make seed`, файл CSV в git не хранится) и данных ленты (`make seed-feed`:
  друзья и посты у 100 тысяч активных пользователей, тексты из `posts.txt`, `make seed-posts-file`, файл в git не хранится).
- Реализации портов (PDO-репозиторий, хешер, токены) пишутся в каждом приложении
  отдельно, но обязаны проходить одни и те же contract-тесты из `core/tests/Contract`.
- Оба приложения дают идентичный HTTP-контракт на одной БД
  для честного нагрузочного сравнения.
- Приложения не зависят друг от друга. Общий код только через `core`.

## Стандарты кода
- PHP 8.4+, `declare(strict_types=1)` в каждом файле.
- SOLID, Clean Architecture, зависимости направлены внутрь (к Domain).
- Dependency injection, без статических вызовов и глобального состояния.
- Value objects и immutable-объекты там, где это уместно.
- Интерфейсы для всего, что пересекает границу слоя.
- Осмысленные имена, без аббревиатур и суффиксов-мусора.
- Без фреймворк-специфичных shortcut'ов в общем коде.

## Жёсткие ограничения задания
- Без ORM. Только PDO с параметризованными запросами (prepared statements).
  Конкатенация пользовательских данных в SQL запрещена.
- Пароли только через `password_hash` (argon2id), в открытом виде не хранить и не логировать.
- Не использовать шардирование. Кэширование разрешено только в рамках ДЗ «Лента постов» (ветка `homework-feed`,
  отчёт в `docs/homework-feed/`): Redis хранит ленту друзей (ZSET с идентификаторами, последние 1000) и тела постов.
  Источник истины остаётся PostgreSQL, Redis можно потерять и перестроить из БД.
  Асинхронный fan-out ленты идёт через Redis Streams, обработчик (воркер) в том же коде приложения, отдельным процессом.
  Клиент Redis — расширение `phpredis` (в Dockerfile), composer-зависимость не добавляется.
  Для `/post/get` и остальных эндпоинтов вне ленты кэширование не вводится.
- Репликация разрешена только в рамках ДЗ «Репликация» (ветка `homework-replication`, отчёт в `docs/homework-replication/`):
  потоковая репликация PostgreSQL (1 primary + 2 standby), чтение `GET /user/get/{id}` и `GET /user/search`
  со standby, запись и логин на primary. Балансировка чтения только через HAProxy на уровне инфраструктуры,
  в коде приложений выбор «куда читать» делается в composition root (какой PDO получает репозиторий use case'а),
  а не подменой драйвера или разбором SQL.
- Индексы не добавлять сверх первичного ключа и ограничений, нужных для корректности,
  кроме обоснованных замером: `users (last_name varchar_pattern_ops, first_name varchar_pattern_ops)`
  для `GET /user/search` (ДЗ «Производительность индексов», `db/migrations/002_…`, отчёт в `docs/homework-indexes/`).
- Монолит: никаких отдельных сервисов, очередей, брокеров. Инфраструктура БД и наблюдаемости (реплики PostgreSQL,
  HAProxy, Prometheus, postgres_exporter, cAdvisor, Grafana) сервисами приложения не считается; приложений остаётся два.
  Redis (кэш ленты и Redis Streams) тоже инфраструктура, а не сервис приложения; воркер fan-out — тот же код
  приложения, запущенный отдельным процессом, а не отдельный сервис.

## Правила работы
- Код пишем только по явной просьбе. Сначала обсуждаем дизайн.
- Не добавлять зависимости без согласования.
- Любое изменение контракта сначала вносится в `docs/openapi.json`,
  затем реализуется в обоих приложениях.
- Любая новая реализация порта сначала получает contract-тест в `core`,
  затем реализуется в обоих приложениях.
- Изменение схемы БД: сначала `db/migrations`, затем оба репозитория.
- Реализации Infrastructure в обоих приложениях эквивалентны по подходу
  (PDO, prepared statements, argon2id, одинаковые параметры хеширования),
  чтобы нагрузочный тест сравнивал фреймворки, а не разные реализации.
- Любое изменение в `core` не должно ломать оба приложения.
- Нагрузочные замеры только в режиме bench (`make bench-up`): одинаковые лимиты
  ресурсов, `php.ini`, `php-fpm.conf`, без bind mount.
- Все узлы PostgreSQL (primary и standby) получают одинаковые лимиты CPU и памяти и один `postgresql.conf`.
  Замеры до и после репликации сравнимы только на одинаковых лимитах.
- Мониторинг (Prometheus, postgres_exporter, cAdvisor, Grafana) живёт в compose-профиле `monitoring`
  (`make monitoring-up`) и по умолчанию не запускается. Если замер сделан с профилем, это указывается в отчёте.
- Изменение топологии БД: сначала `social-network-docker/postgres` и compose, затем роутинг в обоих приложениях.
  Роутинг чтения и записи в обоих приложениях эквивалентен по подходу.

- Контракт ДЗ «Лента постов» берётся из спецификации OTUS (`/friend/set|delete`, `/post/create|update|delete|get|feed`),
  но с нашими именами полей (camelCase). Отступления от стандартных REST-практик (удаление через `PUT`, камелкейс вместо
  snake_case, `/friend/set` вместо `/friend/add`, односторонняя дружба, 400 на чужой пост и т. п.) комментируются
  в `description` операций `docs/openapi.json` и одной короткой строкой у регистрации маршрутов в обоих приложениях.
- Роутинг чтения в ДЗ «Лента постов» (в composition root обоих приложений): `GET /post/get/{id}` и backfill ленты
  в воркере читают с primary (контракт обещает, что созданный пост сразу доступен), холодная пересборка ленты
  при промахе кэша читает с реплики (устаревание допустимо). Проверки владельца в `/post/update` и `/post/delete` и все записи идут на primary.
- Потеря события между фиксацией в PostgreSQL и `XADD` в Redis Streams (падение процесса между ними) принимается как известное
  ограничение, outbox не вводится; в отчёте `docs/homework-feed/` это описывается явно.
- Индексы для ДЗ «Лента постов» добавляются отдельными миграциями только после замера: `friendships (friend_id, user_id)`
  для подписчиков автора и `posts (author_id, created_at DESC, id DESC)` для сборки ленты; `003` их не содержит.
- Fan-out пишет в ленту подписчика только если её ключ в Redis уже есть (проверка и `ZADD` одним Lua-скриптом):
  память Redis не вмещает ленты миллиона пользователей, остальные ленты собираются лениво при чтении с реплики.
  `/friend/delete` удаляет ключ ленты (пересборка при чтении), `/friend/set` делает backfill только в существующую ленту.
  Ключи кэша получают TTL (вытеснение `volatile-lru`), стрим без TTL ограничивается `MAXLEN ~`.
  Redis без персистентности; префикс ключей, стрим и consumer group у каждого приложения свои (`REDIS_KEY_PREFIX`).
- Лента: Redis только кэш. Запись поста и дружбы сначала в PostgreSQL, затем событие в Redis Streams; потеря ключа ленты
  лечится перестроением из БД. Реализации очереди и кэша в обоих приложениях эквивалентны по подходу.
- Тексты постов для сида: `posts.txt` из OTUS (в git не хранится, как и CSV), отдельная цель Makefile.

## Команды
Определены в `Makefile`, список: `make help`.

## Definition of Done
- Регистрация, логин и получение анкеты работают в обоих приложениях.
- Unit-тесты `core` проходят.
- Postman-коллекция проходит против обоих приложений.
- README содержит инструкцию по локальному запуску.
