# Social Network

Учебный монолит: регистрация, логин и просмотр анкеты по ID.
Два приложения поверх общего ядра бизнес-логики, чтобы потом сравнить их под нагрузкой:

- `apps/native`: чистый PHP
- `apps/symfony`: Symfony
- `frontend/`: простой UI для ручной проверки API (HTML + ES-модули, без сборки)

Статус: `packages/core`, `apps/native` и `apps/symfony` реализованы, Postman-коллекция проходит против обоих приложений.

## Структура

```
packages/core/           бизнес-логика: Domain + Application (порты-интерфейсы)
apps/native/             чистый PHP: Infrastructure + Presentation
apps/symfony/            Symfony: Infrastructure + Presentation
frontend/                статический UI: регистрация, вход, анкета
db/migrations/           общая SQL-схема
social-network-docker/   Dockerfile'ы и конфиги php-fpm, nginx, postgres
docs/                    openapi.json, Postman-коллекция, отчёты по ДЗ (индексы, репликация)
```

## Локальный запуск

Всё выполняется в контейнерах: локальные PHP, Composer и PostgreSQL не нужны.

**Требования**

- Docker с Compose v2 (`docker compose version`) и make.
- Свободные порты 8080, 8081, 8082, 5432 (primary), 5433 и 5434 (реплики), 8404 (статистика HAProxy), 6379 (Redis) (меняются в `.env`, см. ниже).
  Для мониторинга ещё 3000 (Grafana) и 9090 (Prometheus).

**Первый запуск** (порядок важен: зависимости ставятся до старта приложений, потому что код монтируется в контейнеры вместе с `vendor`)

```
make init      # создаст .env из .env.example
make install   # composer install для core и обоих приложений (по composer.lock)
make up        # соберёт образы и поднимет стек в режиме разработки
```

`make init` не перезаписывает существующий `.env`. Значения по умолчанию (`change_me`) подходят для локальной работы;
для чего-то большего поменяйте `POSTGRES_PASSWORD`, `AUTH_TOKEN_SECRET` и `SYMFONY_APP_SECRET`. `AUTH_TOKEN_SECRET` не может быть пустым:
приложения откажутся выдавать токены.

**Проверка, что всё работает**

```
make ps                                                   # postgres должен быть healthy, остальные Up
curl -i http://localhost:8081/user/get/99999999-9999-4999-8999-999999999999   # native
curl -i http://localhost:8082/user/get/99999999-9999-4999-8999-999999999999   # symfony
make test-core test-native test-symfony                  # тесты
```

Ожидаемый ответ на каждый `curl`: `404` с JSON `{"message": "User ... was not found."}`. Это значит, что приложение и БД работают.
Полный сценарий (регистрация, логин, получение анкеты) описан в разделе «Проверка API», а UI для ручной проверки открывается на http://localhost:8080.

**Тестовые данные: миллион анкет**

Положите `people.v2.csv` (формат `Фамилия Имя,YYYY-MM-DD,Город`) в `db/seed/` и выполните на пустой БД:

```
make reset-db && make up && make seed
```

`make seed` (`db/seed/seed.sh` + `load.sql`) загружает CSV через `COPY`, определяет пол по фамилии, догенерирует недостающие
до 1 000 000 анкеты из реальных имён и фамилий и выполняет `ANALYZE`. Неполная последняя строка CSV пропускается.
У всех анкет пароль `seed-password` (один заранее посчитанный хеш argon2id с параметрами приложений). На непустой таблице `users` скрипт
останавливается с ошибкой. Кейсы поиска в `make compare` рассчитаны на эти данные.

**Тестовые данные ленты: друзья и посты**

Для ДЗ «Лента постов» поверх миллиона анкет:

```
make seed-posts-file   # скачать posts.txt (тексты постов OTUS, около 6 МБ) в db/seed/, в git не хранится
make seed-feed         # заполнить пустые friendships и posts (около 2 минут)
make reset-feed        # очистить friendships и posts и сбросить Redis (users остаются)
```

`make seed-feed` (`db/seed/seed-feed.sh` + `feed.sql`) выбирает 100 000 «активных» пользователей (случайно, воспроизводимо) и создаёт
только между ними: около 1,95 млн односторонних связей (у каждого от 3 до 49 друзей, в среднем 19,5; цели выбираются с перекосом,
поэтому у одной «знаменитости» 32 011 подписчиков, у следующих 10 298, 7 423, ...) и 1 000 000 постов (в среднем 10 на автора, до 454,
тексты из `posts.txt` по кругу, время создания за последние 90 дней). Плодовитые авторы не совпадают со «знаменитостями». Размер ленты
(посты друзей до обрезки до 1000): медиана 222, 90-й перцентиль 812, у единиц больше 1000. Таблицы занимают около 850 МБ (`posts`)
и 220 МБ (`friendships`) без индексов сверх первичных ключей. На непустых таблицах скрипт останавливается с ошибкой. Идентификаторы
постов в сиде — UUID v4 (в PostgreSQL 17 нет `uuidv7()`, приложения создают v7, на чтение это не влияет).

**Остановка и сброс**

```
make down                     # остановить стек (данные БД сохраняются)
make reset-db && make up      # удалить данные БД и применить миграции заново
```

Список всех команд: `make help`.

Порты по умолчанию:

| Сервис     | Адрес                 | Переменная в `.env` |
|------------|-----------------------|---------------------|
| native     | http://localhost:8081 | `NATIVE_PORT`       |
| symfony    | http://localhost:8082 | `SYMFONY_PORT`      |
| frontend   | http://localhost:8080 | `FRONTEND_PORT`     |
| PostgreSQL | localhost:5432        | `POSTGRES_PORT`     |

Схема БД из `db/migrations` применяется автоматически только при первом старте на пустом томе.

**Если что-то не работает**

- Порт занят (`port is already allocated`): поменяйте нужный порт в `.env` и выполните `make up`.
- 500 от приложения сразу после клонирования: не выполнен `make install` (нет `vendor`). Выполните его и повторите запрос.
- Symfony: консоль запускайте от `www-data` (`make console c="debug:router"` или `docker compose exec -u www-data php-symfony php bin/console ...`).
  Команда без `-u www-data` выполняется от root и создаёт в `/var/www/symfony-var` файлы, которые php-fpm потом не сможет перезаписать (ошибка 500 «Permission denied»).
  Если это уже случилось: `docker compose exec php-symfony chown -R www-data:www-data /var/www/symfony-var`.
- Нужно изменить схему БД или начать с чистого состояния: `make reset-db && make up`.

Режимы dev и bench, а также нагрузочные замеры описаны ниже в разделах «Режимы» и «Нагрузочные замеры и ёмкость».

## Репликация PostgreSQL

Стек поднимает три узла PostgreSQL: `postgres` (primary) и две реплики `postgres-replica-1` и `postgres-replica-2` на потоковой репликации.
Запись и логин идут на primary (`DB_HOST`), `GET /user/get/{id}` и `GET /user/search` читают с реплик через HAProxy (`DB_READ_HOST`).
Подробности, замеры и эксперимент с аварией мастера: [`docs/homework-replication/README.md`](docs/homework-replication/README.md).

```
make repl-status      # роли узлов, подключённые реплики, лаг
make repl-sync        # кворумная синхронная репликация ANY 1 (replica1, replica2)
make repl-async       # вернуть асинхронную (штатный режим)
make monitoring-up    # Prometheus, postgres_exporter, redis_exporter, cAdvisor, Grafana (http://localhost:3000, профиль monitoring)
make bench-read PHASE=replicas                 # замер чтения (get и search, k6), см. docs/homework-replication/
make bench-write PHASE=write [DURATION=30s]    # нагрузка на запись, клиент считает подтверждённые записи
make repl-failover MODE=async|sync             # kill -9 primary под нагрузкой, promote, подсчёт потерь
make repl-rebuild                              # кластер PostgreSQL с нуля (тома БД удаляются, данные заливаются заново)
```

- Реплики снимают базовую копию с primary при первом старте (`pg_basebackup -R`) и дальше догоняют его сами, в том числе во время
  `make seed`. Состояние: `make repl-status` (перед замерами лаг должен быть 0).
- Эксперимент `make repl-failover` убивает primary и разрушает кластер: после него нужен `make repl-rebuild`. Данные БД удаляются.
- `DB_READ_HOST=postgres make bench-up` возвращает чтение на primary (baseline «одна нода»).
- Если `.env` создан раньше, добавьте в него новые переменные из `.env.example`: пароль репликации, `MONITORING_*`, `GRAFANA_ADMIN_PASSWORD`, порты.

## Лента постов (ДЗ «Лента постов», ветка `homework-feed`)

Друзья (`/friend/set`, `/friend/delete`), посты (`/post/create|update|delete|get`) и лента постов друзей (`/post/feed`).
Контракт и его отступления от спецификации OTUS описаны в `docs/openapi.json`.

**Статус работы** (обновляется по мере выполнения шагов):

- Готово: контракт и Postman-папки, миграция `003` (таблицы `friendships` и `posts`), сервис Redis и phpredis в PHP-образе,
  use case'ы и порты в `core`, оба приложения целиком (PDO, Redis-кэш, очередь на Redis Streams, воркеры `worker-native` и
  `worker-symfony`, HTTP-маршруты): Postman-коллекция проходит против native и symfony (150 проверок каждое), в том числе
  с остановленным Redis.
  `make compare` (около 375 кейсов, включая друзей, посты и ленту) не находит расхождений между приложениями, `make compare-infrastructure`
  подтверждает, что Infrastructure ленты в двух копиях совпадает.
- Готово также: сид друзей и постов (`make seed-feed`), замеры до и после индексов `004` и `005`, отчёт `docs/homework-feed/README.md`.

**Как устроено**

- PostgreSQL остаётся источником истины. Дружба односторонняя: лента строится по тем, кого пользователь добавил сам.
- Redis хранит ленту (ZSET из последних 1000 id) и тела постов с TTL. Он не источник истины и работает без персистентности:
  после потери данных ленты пересобираются из PostgreSQL. Ленты миллиона пользователей в памяти не помещаются, поэтому событие
  о новом посте пишется только в уже существующие ленты, остальные собираются лениво при чтении.
- Событие о новом посте уходит в Redis Streams, воркер раскладывает его по лентам асинхронно, поэтому лента итогово согласована.
  Воркер (`worker-native`, `worker-symfony`) — тот же код приложения отдельным процессом (у Symfony это команда `feed:work`,
  запускается от `www-data`): `make up` запускает воркеры вместе со стеком, логи `make worker-logs`, после правок кода в dev
  `make worker-restart`. При ошибке инфраструктуры воркер завершается и перезапускается docker'ом,
  необработанное событие приходит снова (at-least-once, все операции идемпотентны).
- Если Redis недоступен, чтение ленты идёт напрямую из PostgreSQL (медленнее, но верно), а публикация событий молча пропускается:
  после возвращения Redis ленты собираются заново из БД.
- Настройки Redis: `social-network-docker/redis/redis.conf`, пароль и лимиты в `.env` (`REDIS_PASSWORD`, `REDIS_CPUS`,
  `REDIS_MEMORY`, `REDIS_MAXMEMORY`). Каждое приложение работает со своими ключами и стримом (`REDIS_KEY_PREFIX`: `native` или `symfony`).

**Запуск для проверки**

1. Поднять стек (шаги «Первый запуск» выше): `make init && make install && make up`. Redis и воркер ленты стартуют вместе
   с остальными сервисами.
   Если `.env` создан раньше, добавьте в него `REDIS_*` из `.env.example`.
2. Убедиться, что в БД есть таблицы ДЗ. Миграции применяются только на пустом томе, поэтому на БД, созданной до `003`,
   примените её вручную (реплики получат таблицы по репликации, данные сохраняются):

   ```
   docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 --single-transaction' \
     < db/migrations/003_create_friendships_and_posts.sql
   ```

   Проверка: `docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\dt"'` должна показать
   `users`, `friendships` и `posts`. Повторный запуск `003` завершится ошибкой «relation already exists», это нормально.
   Индексы ленты `004` и `005` применяются так же (на существующий том вручную, ошибка «already exists» при повторе нормальна);
   на чистой БД все миграции применяются сами. Чистая БД с нуля: `make reset-db && make up` (после этого миллион анкет заливается заново, `make seed`).
3. Проверить Redis и воркеры: `make redis-cli c="PING"` отвечает `PONG`, `make ps` показывает `redis` как healthy, а `worker-native`
   и `worker-symfony` как Up; `make worker-logs` содержит строки `feed worker started`.
4. Прогнать Postman-коллекцию против обоих приложений (раздел «Postman-коллекция» ниже): папки «Second user», «Posts»,
   «Friends» и «Feed» проверяют весь контракт ДЗ, включая итоговую согласованность ленты (запросы ленты опрашивают API до 10 секунд).
5. Ручной сценарий (порт 8081 для native, 8082 для Symfony; `Authorization: Bearer <token>` берётся из `/login`):

   ```
   # два пользователя: зарегистрировать и войти (как в разделе «Проверка API»), получить <idA>, <tokenA>, <idB>, <tokenB>

   # B публикует пост, в ответе id поста
   curl -s -H "Authorization: Bearer <tokenB>" -H 'Content-Type: application/json' http://localhost:8081/post/create -d '{"text": "Первый пост B"}'

   # A добавляет B в друзья (204)
   curl -si -X PUT -H "Authorization: Bearer <tokenA>" http://localhost:8081/friend/set/<idB>

   # лента A: пост B появляется (может потребоваться пара секунд, лента итогово согласована)
   curl -s -H "Authorization: Bearer <tokenA>" 'http://localhost:8081/post/feed?offset=0&limit=10'

   # пост по id (без авторизации), изменение и удаление (PUT, 204), удаление друга
   curl -s http://localhost:8081/post/get/<postId>
   curl -si -X PUT -H "Authorization: Bearer <tokenB>" -H 'Content-Type: application/json' http://localhost:8081/post/update -d '{"id": "<postId>", "text": "Изменено"}'
   curl -si -X PUT -H "Authorization: Bearer <tokenB>" http://localhost:8081/post/delete/<postId>
   curl -si -X PUT -H "Authorization: Bearer <tokenA>" http://localhost:8081/friend/delete/<idB>
   ```

6. Мониторинг (необязательно): `make monitoring-up`, панель «Лента постов: Redis и воркеры» на
   <http://localhost:3000/d/feed-redis>: попадания и промахи кэша, память и вытеснения, очередь событий обоих приложений,
   CPU и память Redis, воркеров и php. Остановить: `make monitoring-down`. Нагрузочные замеры делаются без мониторинга.
7. Посмотреть, что лежит в Redis: `make redis-cli c="KEYS '*'"` (на учебных объёмах), `make redis-cli c="INFO memory"`.
   Сбросить кэш (холодный старт, например перед замером): `make redis-flush`.

## Тесты

```
make test-core     # unit-тесты core
make test-native   # интеграционные тесты native (нужен запущенный postgres: make up)
make test-symfony  # интеграционные тесты symfony
```

Интеграционные тесты native и symfony наследуют contract-тесты из `packages/core/tests/Contract` и идут на реальный PostgreSQL.
Каждый тест выполняется в транзакции, которая откатывается, поэтому данные в БД не остаются.

## Проверка API

Контракт описан в `docs/openapi.json`. Пример для native (`http://localhost:8081`), для Symfony порт `8082`:

```
# регистрация, в ответе id
curl -s -H 'Content-Type: application/json' http://localhost:8081/user/register -d '{
  "firstName": "Ivan", "lastName": "Petrov", "birthDate": "1990-05-17",
  "gender": "male", "interests": ["hiking", "chess"], "city": "Moscow", "password": "s3cret-pass!"
}'

# логин, в ответе token
curl -s -H 'Content-Type: application/json' http://localhost:8081/login \
  -d '{"userId": "<id из ответа регистрации>", "password": "s3cret-pass!"}'

# анкета по id
curl -s http://localhost:8081/user/get/<id>

# поиск по префиксу имени и фамилии (регистрозависимый, сортировка по id)
curl -s -G http://localhost:8081/user/search --data-urlencode first_name=Конст --data-urlencode last_name=Оси
```

### Postman-коллекция

В `docs/postman/` лежат коллекция и окружения `native` и `symfony` (в окружении задан `baseUrl`).
Импортируйте их в Postman и запустите Collection Runner с нужным окружением.

То же из командной строки, без установки Postman и newman (нужен только Docker, стек должен быть запущен):

```
cd docs/postman
docker run --rm --network host -v "$PWD":/etc/newman:ro postman/newman \
  run social-network.postman_collection.json -e native.postman_environment.json
```

Для Symfony замените окружение на `symfony.postman_environment.json`. Скрипты коллекции берут адрес через `pm.variables.get('baseUrl')`
(он учитывает окружение), поэтому прогон против symfony действительно идёт в symfony.
Папка «Search users» ищет пользователя, созданного в «Register - success», поэтому сид для коллекции не нужен.
Папки «Second user», «Posts», «Friends» и «Feed» относятся к ДЗ «Лента постов» (ветка `homework-feed`): они описывают контракт
из `docs/openapi.json` и проходят только после реализации методов в обоих приложениях. Лента итогово согласована, поэтому её
запросы опрашивают API до 10 секунд, пока ожидаемое состояние не наступит.
Каждый прогон создаёт в БД двух новых пользователей; чтобы очистить данные: `make reset-db && make up` (сид после этого заливается заново).

## Frontend

Открыть после `make up`: http://localhost:8080. Четыре раздела: регистрация, вход, анкета по id, поиск анкет по началу имени и фамилии.
Переключатель **Backend** в шапке направляет запросы в native или в Symfony, так что оба приложения
проверяются одним интерфейсом. После регистрации интерфейс показывает id: вход выполняется по id, а не по логину.

Без сборки и зависимостей: статика из `frontend/` монтируется в `nginx-frontend`, который заодно проксирует
`/api/native/` и `/api/symfony/` в приложения. Запросы идут на один origin, CORS не нужен.
`nginx-frontend` описан только в `docker-compose.override.yaml`: `make bench-up` его не запускает
и удаляет, если он остался от dev-стека (`--remove-orphans`), чтобы он не влиял на замеры.

Ручная проверка (для каждого backend'а):

1. Регистрация с паролем короче 8 символов: ошибка у поля «Пароль». Затем с корректным паролем: показан id.
2. Вход с неверным паролем: «Неверный идентификатор или пароль». С верным: открывается анкета, вверху «Вы вошли».
3. Анкета по id: поля, интересы списком. Невалидный id: подсказка про UUID. Незнакомый UUID: «Не найдено».
4. Имя вида `<b>x</b>` отображается как текст, а не как разметка.
5. «Выйти» убирает панель сессии; смена backend'а тоже сбрасывает сессию.
6. Поиск «Конст» + «Оси» (на данных `make seed`): список «Найдено: N», ссылки ведут на анкеты; адрес `#/search?first_name=…&last_name=…` можно открыть заново.
   Фамилия из пробелов: ошибка у поля «Начало фамилии». `%` в поле ничего не находит (ищется буквально).

## Режимы

- **dev** (`make up`): код монтируется в контейнеры, opcache перечитывает файлы.
- **bench** (`make bench-up`): код копируется в образ, `composer install --no-dev --classmap-authoritative`, opcache без проверки timestamps, bind mount нет. Нагрузочные замеры проводятся только в этом режиме.

Настройки PHP, php-fpm, nginx и лимиты ресурсов одинаковы для обоих приложений.

## Сверка приложений

`make compare` проверяет, что native и Symfony отвечают на одни и те же запросы одинаково (нужен запущенный стек, dev или bench).
Скрипт `social-network-docker/compare/compare.php` запускается в одноразовом контейнере `php:8.4.26-cli` с `--network host`,
порты берёт из `NATIVE_PORT` и `SYMFONY_PORT` (по умолчанию 8081 и 8082).

Что делает:

- Сначала регистрирует по одному пользователю в каждом приложении, затем отправляет около 375 запросов в оба:
  сценарии регистрации, логина, анкеты и поиска (границы длин, типы, отсутствующие поля, кривой JSON, пустое тело, чужой `Content-Type`),
  а также неизвестные пути, неподдерживаемые методы, слэш в конце пути, `HEAD`, `OPTIONS`.
- Для ДЗ «Лента постов» подготавливает состояние в каждом приложении (пользователь A с токеном, пользователь B с тремя постами, A добавляет
  B в друзья, ждёт, пока лента A наполнится) и сверяет друзей, посты и ленту: заголовок `Authorization` во всех видах (нет, мусор, чужая схема,
  два пробела), границы текста и страницы, изменение и удаление своих и чужих постов с проверкой результата, порядок проверок (авторизация
  раньше тела и валидации), методы, пути, а в конце удаление и возвращение друга с ожиданием ленты. Нужны запущенные воркеры (`make up`).
- Сравнивает статус, `Content-Type`, `Allow` и тело. JSON сравнивается без учёта порядка ключей.
- Значения, которые различаются по природе, перед сравнением заменяются на плейсхолдеры: UUID пользователей и подпись токена.
- Для каждого нового расхождения печатает имя кейса и ответ каждого приложения.
- Код выхода: 0, если новых расхождений нет; 1, если есть новое расхождение или устарела запись в списке известных; 2, если не удалось запустить сверку (стек недоступен).

Известные расхождения перечислены в константе `KNOWN_DIFFERENCES` в `compare.php` (имя кейса и причина). Они печатаются как `known` и на код выхода не влияют.
Сейчас там одно, оставленное намеренно: путь с процентным кодированием (`POST /lo%67in`).
Symfony декодирует путь и находит маршрут `/login`, native сопоставляет путь как есть и отвечает 404.
Если запись из списка перестала соответствовать действительности (расхождение исчезло или кейса с таким именем нет), сверка завершается с ошибкой `STALE`: запись нужно удалить.

Каждый запуск добавляет в БД несколько десятков пользователей и постов; перед замерами нагрузки выполните `make reset-db`.
Кейсы описаны массивом в самом скрипте. Postman-коллекция остаётся проверкой контракта по ассертам, сверка её не заменяет.
Чтобы добавить кейс, допишите вызов `$add(...)` (без авторизации) или `$addApi(...)` (с заголовком `Authorization`, свежим постом,
повтором или проверкой результата) в `compare.php`.

Сверка нашла реальное расхождение: ответ 204 в native содержал `Content-Type: text/html` (PHP добавляет его сам, когда тела нет),
а в Symfony заголовка нет. Native теперь отключает заголовок по умолчанию для ответов без тела.

### Сверка инфраструктуры

`make compare-infrastructure` сравнивает файлы Infrastructure ленты постов (PDO-репозитории, Redis-кэш, очередь событий, генератор id и их тесты)
в `apps/native` и `apps/symfony` после замены namespace и префикса в логах. Классы существуют в двух копиях, потому что приложения не
зависят друг от друга; любое расхождение значит, что нагрузочное сравнение перестало быть честным. Скрипт не требует запущенного стека
и завершается с кодом 1 при расхождении. Меняя такой класс, меняйте оба приложения.

## Нагрузочные замеры и ёмкость

Замеры только в режиме bench: `make bench-up`. Перед серией лучше `make reset-db`, чтобы в БД не копились тестовые пользователи.
Замер `GET /user/get/{id}` в обоих приложениях (регистрирует по пользователю в каждом, прогрев 3 с):

```
make bench-get                              # 32 соединения, 15 с
make bench-get CONCURRENCY=64 DURATION=30
```

Генератор нагрузки (`social-network-docker/bench/load.php`) запускается в одноразовом контейнере `php:8.4.26-cli` с `--network host`.
Он однопоточный и работает на том же хосте, что и стек, поэтому абсолютные цифры годятся как ориентир. Сравнивать стоит прогоны между собой.

**Что ограничивает пропускную способность**

- `/login` и `/user/register` упираются в argon2id (m=65536, t=4, p=1): один хеш ≈ 98 мс CPU и 64 МБ памяти.
  На лимите 2 CPU это порядка 20 req/s на приложение, независимо от фреймворка. Эти эндпоинты сравнивать фреймворки не помогают.
- Фреймворки честнее сравнивать по `GET /user/get/{id}`: хеша там нет, остаётся роутинг, DI, запрос в PostgreSQL и сериализация.
- Размер пула php-fpm: `PHP_FPM_MAX_CHILDREN=4` (ENV в `social-network-docker/php/Dockerfile`).
  Пик памяти при логинах ≈ 22 МБ + 65 МБ × воркеры при лимите контейнера 512 МБ: 4 воркера ≈ 280 МБ, 6 ≈ 413 МБ, 8 на грани OOM,
  при 16 контейнер падает по OOM (502) уже примерно с 24 параллельных логинов.
  Больше воркеров не ускоряет: при лимите 2 CPU 4 воркера дают наибольший RPS и меньший p99.
  Чтобы повторить замер с другим значением, поменяйте ENV в Dockerfile и выполните `make bench-up`.
- Подключения к PostgreSQL постоянные (`PDO::ATTR_PERSISTENT`): каждый воркер держит своё соединение, так что их ровно столько, сколько воркеров.
  Без этого каждый запрос открывал новое соединение, и на ~470 соединениях в секунду кончались локальные порты (`Address not available`, TIME_WAIT).
  Следите, чтобы число воркеров × число php-контейнеров было меньше `max_connections` PostgreSQL (200).

Ориентир на 4 воркерах (32 соединения, 15 с, три прогона подряд на чистой БД, Symfony 8.1): native ≈ 12 800–13 100 req/s (p99 ≈ 20 мс), symfony ≈ 3 500–3 600 req/s (p99 ≈ 46 мс).

### Замер поиска `GET /user/search` (k6)

Нужен стек bench с миллионом анкет: `make reset-db && make bench-up && make seed`. Порядок важен: `make reset-db` удаляет и сид.

```
make bench-search PHASE=before      # до индекса
make bench-search PHASE=after       # после индекса
make bench-plot                     # графики и таблицы в docs/homework-indexes/
```

- Генератор: [k6](https://k6.io) в одноразовом контейнере `grafana/k6:1.3.0` с `--network host`, сценарий `social-network-docker/bench/search.js`.
  Модель замкнутая (`constant-vus`): N виртуальных пользователей шлют запросы без пауз, соединения переиспользуются (keep-alive).
- Уровни 1/10/100/1000 одновременных запросов, на каждый прогрев 10 с без учёта и замер 60 с, сначала native, затем Symfony.
  Переопределяется через `LEVELS`, `WARMUP`, `DURATION`, `APPS`, например `make bench-search PHASE=before LEVELS="1 10" DURATION=30s`.
- Запросы берутся случайно из `social-network-docker/bench/search-queries.csv`: 1000 пар «3 буквы имени, 3 буквы фамилии»
  из случайных анкет. Файл в git, чтобы до и после индекса гонялся один набор; пересоздать: `make bench-search-queries`.
- Итоги k6 в JSON: `docs/homework-indexes/results/<phase>/<app>-c<N>.json`. Графики строит `matplotlib` в одноразовом образе
  (`social-network-docker/bench/plot/`).
- `make compare` и регистрации добавляют пользователей сверх миллиона; перед замером проверьте `SELECT count(*) FROM users`.
- Отчёт с результатами до и после индекса: [`docs/homework-indexes/README.md`](docs/homework-indexes/README.md).

### Замеры ленты постов (k6)

Для ДЗ «Лента постов» (нужны `make bench-up`, `make seed`, `make seed-feed` и нулевой лаг репликации):

```
make bench-feed-readers                     # 100 000 читателей с токенами в social-network-docker/bench/feed-readers.csv (в git не хранится)
make bench-feed PHASE=before-indexes        # nocache, cold, warm и post на обоих приложениях, уровни 1, 10, 50, 100 VU
make bench-fanout PHASE=before-indexes      # задержка fan-out: малый, средний автор и «знаменитость»
make explain-feed PHASE=before-indexes      # EXPLAIN (ANALYZE, BUFFERS) запросов ленты в docs/homework-feed/explain/
```

Параметры `bench-feed`: `MODES` (`nocache cold warm post`), `LEVELS`, `DURATION` (30s), `WARMUP` (10s), `WARM_SIZE` (2000 читателей в `warm`),
`DRAIN_TIMEOUT` (120 с на разбор очереди), `APPS`. Итоги лежат в `docs/homework-feed/results/<PHASE>/`: JSON k6 на каждый прогон,
`node-stats.csv` (нагрузка на узлы БД), `redis-stats.csv` (попадания, промахи, вытеснения, память и очередь Redis),
`post-drain.csv` (скорость разбора очереди воркером), `docker-stats.log` (CPU и память контейнеров).

Что означают режимы:

- `nocache`: Redis недоступен (заблокирован сменой пароля, остановленный контейнер дал бы лишнюю секунду на разрешение имени), приложение собирает ленту из БД на каждый запрос (чтение с реплики);
- `cold`: кэш сброшен, каждый запрос от нового читателя: промах, сборка из БД, запись в Redis (если читателей не хватило и они пошли
  по второму кругу, замер завершается ошибкой);
- `warm`: ленты читателей уже в Redis, это попадания в кэш (перед замером кэш заполняется, `redis-stats.csv` даёт hit ratio);
- `post`: `POST /post/create` и асинхронный fan-out; после нагрузки замеряется, как быстро воркер разбирает очередь.

Особенности, о которых стоит знать:

- php перезапускается **вместе с nginx**: при одновременном перезапуске двух контейнеров они меняются IP, а nginx держит адрес, разрешённый
  при старте, и порт одного приложения начинает вести в контейнер другого (подписи native и symfony в результатах тогда путаются).
  `feed.sh` перезапускает nginx и проверяет маршрутизацию по заголовку `Cache-Control` (его отдаёт только Symfony).
- Заполнение кэша перед `warm` равно числу холодных сборок ленты: без индекса `posts(author_id, ...)` это около полусекунды на ленту.
- Без индекса `friendships(friend_id, user_id)` fan-out каждого поста сканирует всю таблицу связей: воркер разбирает около 9 событий в секунду на
  узле в 0,5 CPU, очередь при записи в сотни постов в секунду растёт. Хвост очереди перед замером дожидается и обрезается.
- Пробные прогоны (`PHASE=smoke`) в git не попадают.

## Отладка (Xdebug)

Xdebug есть только в dev-образе и по умолчанию выключен. В bench его нет.

1. `make debug-on` (вернуть обратно: `make debug-off`).
2. В IDE включите прослушивание порта **9003** и настройте маппинг путей: корень репозитория на хосте ↔ `/app` в контейнере.
   Для PhpStorm: Server с любым именем, Use path mappings, ваш каталог проекта → `/app`.
3. Отправьте запрос с триггером: параметр `?XDEBUG_TRIGGER=1` (удобно в Postman), cookie `XDEBUG_SESSION` или расширение браузера.

Контейнер обращается к IDE по адресу `host.docker.internal`; на Linux он пробрасывается через `extra_hosts` в `docker-compose.override.yaml`.
В dev таймауты php-fpm и nginx сняты, чтобы запрос не обрывался на точке останова.

## Что положить в `docs/`

- `openapi.json`: спецификация из задания (источник истины для контракта).
- `postman/social-network.postman_collection.json`: Postman-коллекция.
- `homework-indexes/`: отчёт ДЗ «Производительность индексов» (`README.md`), графики, итоги k6 и EXPLAIN.
- `homework-feed/`: отчёт ДЗ «Лента постов» (`README.md`), итоги k6 и планы запросов (`results/`, `explain/`).
- `homework-replication/`: отчёт ДЗ «Репликация» (`README.md`), итоги k6 и экспериментов в `results/`, скриншоты дашбордов в `img/`.
