# Social Network

Учебный монолит: регистрация, логин и просмотр анкеты по ID.
Два приложения поверх общего ядра бизнес-логики, чтобы потом сравнить их под нагрузкой:

- `apps/native`: чистый PHP
- `apps/symfony`: Symfony
- `frontend/`: простой UI для ручной проверки API (HTML + ES-модули, без сборки)

Статус: `packages/core`, `apps/native` и `apps/symfony` реализованы, Postman-коллекция проходит против обоих приложений.

## Структура

```
packages/core/           бизнес-логика: Domain + Application (порты-интерфейсы)
apps/native/             чистый PHP: Infrastructure + Presentation
apps/symfony/            Symfony: Infrastructure + Presentation
frontend/                статический UI: регистрация, вход, анкета
db/migrations/           общая SQL-схема
social-network-docker/   Dockerfile'ы и конфиги php-fpm, nginx, postgres
docs/                    openapi.json, Postman-коллекция
```

## Локальный запуск

Всё выполняется в контейнерах: локальные PHP, Composer и PostgreSQL не нужны.

**Требования**

- Docker с Compose v2 (`docker compose version`) и make.
- Свободные порты 8080, 8081, 8082 и 5432 (меняются в `.env`, см. ниже).

**Первый запуск** (порядок важен: зависимости ставятся до старта приложений, потому что код монтируется в контейнеры вместе с `vendor`)

```
make init      # создаст .env из .env.example
make install   # composer install для core и обоих приложений (по composer.lock)
make up        # соберёт образы и поднимет стек в режиме разработки
```

`make init` не перезаписывает существующий `.env`. Значения по умолчанию (`change_me`) подходят для локальной работы;
для чего-то большего поменяйте `POSTGRES_PASSWORD`, `AUTH_TOKEN_SECRET` и `SYMFONY_APP_SECRET`. `AUTH_TOKEN_SECRET` не может быть пустым:
приложения откажутся выдавать токены.

**Проверка, что всё работает**

```
make ps                                                   # postgres должен быть healthy, остальные Up
curl -i http://localhost:8081/user/get/99999999-9999-4999-8999-999999999999   # native
curl -i http://localhost:8082/user/get/99999999-9999-4999-8999-999999999999   # symfony
make test-core test-native test-symfony                  # тесты
```

Ожидаемый ответ на каждый `curl`: `404` с JSON `{"message": "User ... was not found."}`. Это значит, что приложение и БД работают.
Полный сценарий (регистрация, логин, получение анкеты) описан в разделе «Проверка API», а UI для ручной проверки открывается на http://localhost:8080.

**Остановка и сброс**

```
make down                     # остановить стек (данные БД сохраняются)
make reset-db && make up      # удалить данные БД и применить миграции заново
```

Список всех команд: `make help`.

Порты по умолчанию:

| Сервис     | Адрес                 | Переменная в `.env` |
|------------|-----------------------|---------------------|
| native     | http://localhost:8081 | `NATIVE_PORT`       |
| symfony    | http://localhost:8082 | `SYMFONY_PORT`      |
| frontend   | http://localhost:8080 | `FRONTEND_PORT`     |
| PostgreSQL | localhost:5432        | `POSTGRES_PORT`     |

Схема БД из `db/migrations` применяется автоматически только при первом старте на пустом томе.

**Если что-то не работает**

- Порт занят (`port is already allocated`): поменяйте нужный порт в `.env` и выполните `make up`.
- 500 от приложения сразу после клонирования: не выполнен `make install` (нет `vendor`). Выполните его и повторите запрос.
- Symfony: консоль запускайте от `www-data` (`make console c="debug:router"` или `docker compose exec -u www-data php-symfony php bin/console ...`).
  Команда без `-u www-data` выполняется от root и создаёт в `/var/www/symfony-var` файлы, которые php-fpm потом не сможет перезаписать (ошибка 500 «Permission denied»).
  Если это уже случилось: `docker compose exec php-symfony chown -R www-data:www-data /var/www/symfony-var`.
- Нужно изменить схему БД или начать с чистого состояния: `make reset-db && make up`.

Режимы dev и bench, а также нагрузочные замеры описаны ниже в разделах «Режимы» и «Нагрузочные замеры и ёмкость».

## Тесты

```
make test-core     # unit-тесты core
make test-native   # интеграционные тесты native (нужен запущенный postgres: make up)
make test-symfony  # интеграционные тесты symfony
```

Интеграционные тесты native и symfony наследуют contract-тесты из `packages/core/tests/Contract` и идут на реальный PostgreSQL.
Каждый тест выполняется в транзакции, которая откатывается, поэтому данные в БД не остаются.

## Проверка API

Контракт описан в `docs/openapi.json`. Пример для native (`http://localhost:8081`), для Symfony порт `8082`:

```
# регистрация, в ответе id
curl -s -H 'Content-Type: application/json' http://localhost:8081/user/register -d '{
  "firstName": "Ivan", "lastName": "Petrov", "birthDate": "1990-05-17",
  "gender": "male", "interests": ["hiking", "chess"], "city": "Moscow", "password": "s3cret-pass!"
}'

# логин, в ответе token
curl -s -H 'Content-Type: application/json' http://localhost:8081/login \
  -d '{"userId": "<id из ответа регистрации>", "password": "s3cret-pass!"}'

# анкета по id
curl -s http://localhost:8081/user/get/<id>
```

### Postman-коллекция

В `docs/postman/` лежат коллекция и окружения `native` и `symfony` (в окружении задан `baseUrl`).
Импортируйте их в Postman и запустите Collection Runner с нужным окружением.

То же из командной строки, без установки Postman и newman (нужен только Docker, стек должен быть запущен):

```
cd docs/postman
docker run --rm --network host -v "$PWD":/etc/newman:ro postman/newman \
  run social-network.postman_collection.json -e native.postman_environment.json
```

Для Symfony замените окружение на `symfony.postman_environment.json`.
Каждый прогон создаёт в БД нового пользователя; чтобы очистить данные: `make reset-db && make up`.

## Frontend

Открыть после `make up`: http://localhost:8080. Три раздела: регистрация, вход, анкета по id.
Переключатель **Backend** в шапке направляет запросы в native или в Symfony, так что оба приложения
проверяются одним интерфейсом. После регистрации интерфейс показывает id: вход выполняется по id, а не по логину.

Без сборки и зависимостей: статика из `frontend/` монтируется в `nginx-frontend`, который заодно проксирует
`/api/native/` и `/api/symfony/` в приложения. Запросы идут на один origin, CORS не нужен.
`nginx-frontend` описан только в `docker-compose.override.yaml`: `make bench-up` его не запускает
и удаляет, если он остался от dev-стека (`--remove-orphans`), чтобы он не влиял на замеры.

Ручная проверка (для каждого backend'а):

1. Регистрация с паролем короче 8 символов: ошибка у поля «Пароль». Затем с корректным паролем: показан id.
2. Вход с неверным паролем: «Неверный идентификатор или пароль». С верным: открывается анкета, вверху «Вы вошли».
3. Анкета по id: поля, интересы списком. Невалидный id: подсказка про UUID. Незнакомый UUID: «Не найдено».
4. Имя вида `<b>x</b>` отображается как текст, а не как разметка.
5. «Выйти» убирает панель сессии; смена backend'а тоже сбрасывает сессию.

## Режимы

- **dev** (`make up`): код монтируется в контейнеры, opcache перечитывает файлы.
- **bench** (`make bench-up`): код копируется в образ, `composer install --no-dev --classmap-authoritative`, opcache без проверки timestamps, bind mount нет. Нагрузочные замеры проводятся только в этом режиме.

Настройки PHP, php-fpm, nginx и лимиты ресурсов одинаковы для обоих приложений.

## Сверка приложений

`make compare` проверяет, что native и Symfony отвечают на одни и те же запросы одинаково (нужен запущенный стек, dev или bench).
Скрипт `social-network-docker/compare/compare.php` запускается в одноразовом контейнере `php:8.4.26-cli` с `--network host`,
порты берёт из `NATIVE_PORT` и `SYMFONY_PORT` (по умолчанию 8081 и 8082).

Что делает:

- Сначала регистрирует по одному пользователю в каждом приложении, затем отправляет около 110 запросов в оба:
  сценарии регистрации, логина и анкеты (границы длин, типы, отсутствующие поля, кривой JSON, пустое тело, чужой `Content-Type`),
  а также неизвестные пути, неподдерживаемые методы, слэш в конце пути, `HEAD`, `OPTIONS`.
- Сравнивает статус, `Content-Type`, `Allow` и тело. JSON сравнивается без учёта порядка ключей.
- Значения, которые различаются по природе, перед сравнением заменяются на плейсхолдеры: UUID пользователей и подпись токена.
- Для каждого нового расхождения печатает имя кейса и ответ каждого приложения.
- Код выхода: 0, если новых расхождений нет; 1, если есть новое расхождение или устарела запись в списке известных; 2, если не удалось запустить сверку (стек недоступен).

Известные расхождения перечислены в константе `KNOWN_DIFFERENCES` в `compare.php` (имя кейса и причина). Они печатаются как `known` и на код выхода не влияют.
Сейчас там одно, оставленное намеренно: путь с процентным кодированием (`POST /lo%67in`).
Symfony декодирует путь и находит маршрут `/login`, native сопоставляет путь как есть и отвечает 404.
Если запись из списка перестала соответствовать действительности (расхождение исчезло или кейса с таким именем нет), сверка завершается с ошибкой `STALE`: запись нужно удалить.

Каждый запуск добавляет в БД несколько десятков пользователей; перед замерами нагрузки выполните `make reset-db`.
Кейсы описаны массивом в самом скрипте. Postman-коллекция остаётся проверкой контракта по ассертам, сверка её не заменяет.
Чтобы добавить кейс, допишите вызов `$add(...)` в `compare.php`.

## Нагрузочные замеры и ёмкость

Замеры только в режиме bench: `make bench-up`. Перед серией лучше `make reset-db`, чтобы в БД не копились тестовые пользователи.
Замер `GET /user/get/{id}` в обоих приложениях (регистрирует по пользователю в каждом, прогрев 3 с):

```
make bench-get                              # 32 соединения, 15 с
make bench-get CONCURRENCY=64 DURATION=30
```

Генератор нагрузки (`social-network-docker/bench/load.php`) запускается в одноразовом контейнере `php:8.4.26-cli` с `--network host`.
Он однопоточный и работает на том же хосте, что и стек, поэтому абсолютные цифры годятся как ориентир. Сравнивать стоит прогоны между собой.

**Что ограничивает пропускную способность**

- `/login` и `/user/register` упираются в argon2id (m=65536, t=4, p=1): один хеш ≈ 98 мс CPU и 64 МБ памяти.
  На лимите 2 CPU это порядка 20 req/s на приложение, независимо от фреймворка. Эти эндпоинты сравнивать фреймворки не помогают.
- Фреймворки честнее сравнивать по `GET /user/get/{id}`: хеша там нет, остаётся роутинг, DI, запрос в PostgreSQL и сериализация.
- Размер пула php-fpm: `PHP_FPM_MAX_CHILDREN=4` (ENV в `social-network-docker/php/Dockerfile`).
  Пик памяти при логинах ≈ 22 МБ + 65 МБ × воркеры при лимите контейнера 512 МБ: 4 воркера ≈ 280 МБ, 6 ≈ 413 МБ, 8 на грани OOM,
  при 16 контейнер падает по OOM (502) уже примерно с 24 параллельных логинов.
  Больше воркеров не ускоряет: при лимите 2 CPU 4 воркера дают наибольший RPS и меньший p99.
  Чтобы повторить замер с другим значением, поменяйте ENV в Dockerfile и выполните `make bench-up`.
- Подключения к PostgreSQL постоянные (`PDO::ATTR_PERSISTENT`): каждый воркер держит своё соединение, так что их ровно столько, сколько воркеров.
  Без этого каждый запрос открывал новое соединение, и на ~470 соединениях в секунду кончались локальные порты (`Address not available`, TIME_WAIT).
  Следите, чтобы число воркеров × число php-контейнеров было меньше `max_connections` PostgreSQL (200).

Ориентир на 4 воркерах (32 соединения, 15 с, три прогона подряд на чистой БД, Symfony 8.1): native ≈ 12 800–13 100 req/s (p99 ≈ 20 мс), symfony ≈ 3 500–3 600 req/s (p99 ≈ 46 мс).

## Отладка (Xdebug)

Xdebug есть только в dev-образе и по умолчанию выключен. В bench его нет.

1. `make debug-on` (вернуть обратно: `make debug-off`).
2. В IDE включите прослушивание порта **9003** и настройте маппинг путей: корень репозитория на хосте ↔ `/app` в контейнере.
   Для PhpStorm: Server с любым именем, Use path mappings, ваш каталог проекта → `/app`.
3. Отправьте запрос с триггером: параметр `?XDEBUG_TRIGGER=1` (удобно в Postman), cookie `XDEBUG_SESSION` или расширение браузера.

Контейнер обращается к IDE по адресу `host.docker.internal`; на Linux он пробрасывается через `extra_hosts` в `docker-compose.override.yaml`.
В dev таймауты php-fpm и nginx сняты, чтобы запрос не обрывался на точке останова.
