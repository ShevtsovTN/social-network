# ДЗ «Лента постов от друзей»

Лента постов друзей для учебной социальной сети: API друзей и постов, лента из кэша (Redis), асинхронное обновление лент
через очередь (Redis Streams) и замеры до и после индексов. Приложений два (чистый PHP и Symfony), бизнес-логика общая (`packages/core`),
HTTP-контракт идентичен. Контракт: `docs/openapi.json`, запуск и ручная проверка: раздел «Лента постов» в корневом `README.md`.

## 1. Что реализовано

| Метод | Назначение |
|---|---|
| `PUT /friend/set/{user_id}`, `PUT /friend/delete/{user_id}` | добавить и удалить друга (дружба односторонняя) |
| `POST /post/create`, `PUT /post/update`, `PUT /post/delete/{id}`, `GET /post/get/{id}` | CRUD постов (изменение и удаление через `PUT`, как в спецификации OTUS) |
| `GET /post/feed?offset&limit` | лента постов друзей, новые первыми, не больше 1000 последних |

Нестандартные места (camelCase в полях, `PUT` для удаления, `/friend/set` вместо `/friend/add`, 404 на чужой пост, 204 без тела)
помечены в `description` операций `docs/openapi.json` и одной строкой у маршрутов в обоих приложениях.

## 2. Схема БД

- `friendships (user_id, friend_id, created_at)`, первичный ключ `(user_id, friend_id)`, `CHECK (user_id <> friend_id)`.
  «user_id добавил friend_id»; лента пользователя строится по тем, кого он добавил.
- `posts (id UUID, author_id, text VARCHAR(2000), created_at)`, id генерирует приложение (UUIDv7: порядок по времени).
  Порядок ленты везде `created_at DESC, id DESC`.
- Миграция `003` создаёт таблицы без индексов сверх первичных ключей. Индексы добавлены по результатам замера отдельными миграциями:
  - `004`: `friendships (friend_id, user_id)` для подписчиков автора (fan-out);
  - `005`: `posts (author_id, created_at DESC, id DESC)` для последних постов автора (сборка ленты, backfill).

## 3. Как устроена лента

- **Источник истины — PostgreSQL**, Redis только кэш без персистентности, его можно потерять и перестроить.
- **Лента — ZSET `feed:<userId>`**: элементы — id постов, score — время создания в микросекундах, обрезка до 1000 (`ZREMRANGEBYRANK`).
  Служебный элемент со score 0 отличает пустую ленту от отсутствующей. Тела постов лежат отдельно (`post:<id>`).
  Ключи получают TTL (3600 с), память ограничена (`maxmemory 384mb`, `volatile-lru`).
- **Чтение** (`/post/feed`): есть ключ — страница берётся из ZSET, тела из `post:*`; нет ключа — лента собирается запросом к реплике
  (`friendships JOIN posts ... LIMIT 1000`), кладётся в Redis, отдаётся страница. Если Redis недоступен, лента читается из БД на каждый запрос.
- **Запись поста**: INSERT в PostgreSQL, затем событие в Redis Streams (`XADD`), ответ клиенту сразу.
- **Fan-out**: воркер (тот же код приложения отдельным процессом: `worker-native`, `worker-symfony`) читает стрим consumer group'ой,
  берёт подписчиков автора страницами по 500 и добавляет пост в ленту подписчика только если её ключ в Redis уже есть
  (проверка и `ZADD` одним Lua-скриптом). Лент миллиона пользователей в памяти нет, остальные собираются лениво при чтении.
- **Друзья**: `/friend/set` делает backfill последних постов друга в существующую ленту, `/friend/delete` удаляет ключ ленты (пересборка при чтении).
- **Надёжность воркера**: at-least-once (XACK после обработки, XAUTOCLAIM для зависших событий, 30 с), операции идемпотентны,
  при ошибке инфраструктуры воркер завершается и перезапускается docker'ом.

Почему асинхронно, а не в запросе: цена записи поста не зависит от числа подписчиков (у «знаменитости» их 32 тысячи).
Платим итоговой согласованностью: пост появляется в ленте подписчика через единицы миллисекунд при нормальной работе (раздел 6.4).

## 4. Стенд и данные

- Режим bench (`make bench-up`): код в образе, без bind mount, один `php.ini` и `php-fpm.conf` на оба приложения.
  PostgreSQL: primary и две реплики, по 0,5 CPU и 1 ГБ каждая, один `postgresql.conf`, читающие запросы идут на реплики через HAProxy.
  Redis: 1 CPU, 512 МБ (`maxmemory 384mb`). Воркеры: по 1 CPU и 256 МБ. Мониторинг (профиль `monitoring`) не запускался.
- Данные (`make seed`, `make seed-feed`, детерминированно): 1 000 000 анкет, из них 100 000 активных; 1 947 293 связи
  (в среднем около 19,5 друга, степень 5–50, цели выбираются неравномерно); 1 000 000 постов за последние 90 дней с текстами из `posts.txt` (OTUS).
  Распределение «звёздное»: у самой популярной «знаменитости» 32 011 подписчиков и 494 поста, у типичного пользователя 20 друзей,
  в его ленте около 700 постов. Размеры: `posts` 835 МБ, `friendships` 127 МБ, `friendships_pkey` 92 МБ, индексы `004` 92 МБ и `005` 61 МБ.
  Идентификаторы постов в сиде UUIDv4 (в приложениях UUIDv7), порядок ленты от этого не зависит.
- Нагрузка: k6 (`grafana/k6:1.3.0`), 20 000 читателей с токенами, 1, 10, 50 и 100 виртуальных пользователей, прогрев 10 с и замер 30 с.
  90% запросов ленты — первая страница. Таблицы ниже: пропускная способность (запросов в секунду) · p50/p95 в мс.

## 6. Результаты

### 6.1. EXPLAIN (ANALYZE, BUFFERS) на реплике

| № | Запрос | До, мс | После, мс | Страниц прочитано до → после | План после |
|---:|---|---:|---:|---|---|
| 1 | подписчики обычного автора (20), `LIMIT 500` | 187 | 0,013 | 16 300 → 5 | Index Only Scan по `friendships_friend_id_user_id_idx` |
| 2 | подписчики «знаменитости» (32 011), первые 500 | 0,39 | 0,07 | 183 → 7 | тот же индекс |
| 3 | сборка ленты читателя (20 друзей, 703 поста), `LIMIT 1000` | 799 | 0,28 | 107 000 → 541 | Index Only Scan по `posts_author_id_created_at_id_idx` на каждого друга, затем сортировка |
| 4 | backfill обычного автора (6 постов) | 677 | 0,026 | 107 000 → 8 | Index Only Scan по индексу постов |
| 5 | backfill «знаменитости» (494 поста) | 700 | 0,087 | 107 000 → 339 | тот же индекс |

Без индексов оба запроса, которые отвечают за скорость ленты, читают таблицу целиком (Parallel Seq Scan): у `friendships` нет индекса
по `friend_id`, потому что первичный ключ `(user_id, friend_id)` начинается с `user_id`, а у `posts` нет индекса по `author_id`.
Таблица `posts` больше `shared_buffers` (256 МБ), поэтому даже повторный запуск читает страницы с диска (по кэшу ОС).
У «знаменитости» запрос 2 быстрый и без индекса: подписчиков много, они разбросаны по первичному ключу, и планировщик идёт по нему
в порядке `user_id`, набирая 500 строк за 183 страницы. У обычного автора таких строк 20, и поиск приходится вести перебором всей таблицы.
После индексов все пять запросов выполняются за доли миллисекунды и читают единицы или сотни страниц.

### 6.2. Чтение ленты

**`nocache`: Redis недоступен, лента собирается из БД на каждый запрос (чтение с реплики)**

| VU | native до | native после | symfony до | symfony после |
|---:|---|---|---|---|
| 1 | 1 · 863/923 | 775 · 1/2 | 1 · 799/879 | 644 · 1/2 |
| 10 | 3 · 3504/4147 | 1713 · 4/9 | 3 · 3598/4129 | 1537 · 5/11 |
| 50 | 3 · 17315/19203 | 1696 · 25/51 | 3 · 16710/18597 | 1531 · 25/56 |
| 100 | 3 · 30001/30019 · ошибок 58% | 1719 · 59/78 | 3 · 30001/30023 · ошибок 56% | 1525 · 71/80 |

До индексов одна сборка занимает около 0,8 с и упирается в реплики с 0,5 CPU: больше трёх запросов в секунду не выходит ни у одного приложения,
задержка растёт с числом пользователей почти линейно (очередь на репликах), а при 100 VU больше половины запросов не укладываются в таймаут k6 в 30 с.
После индексов сборка занимает доли миллисекунды, пропускная способность вырастает до 1,5–1,7 тысячи запросов в секунду,
и даже без кэша лента остаётся рабочей. Фаза `nocache` — запасной путь при отказе Redis.

**`cold`: кэш сброшен, каждый запрос от нового читателя (промах, сборка из БД, запись в Redis)**

| VU | native до | native после | symfony до | symfony после |
|---:|---|---|---|---|
| 1 | 3 · 303/398 | 525 · 2/3 | 3 · 360/399 | 451 · 2/3 |
| 10 | 5 · 1591/2700 | 1268 · 8/11 | 4 · 1996/2803 | 1143 · 9/12 |
| 50 | 5 · 9646/10603 | 1259 · 39/45 | 4 · 11195/12224 | 1138 · 44/49 |
| 100 | 5 · 19201/20797 | 1228 · 81/91 | 4 · 23911/25597 | 1136 · 88/96 |

Это сценарий «много новых читателей сразу» (после рестарта Redis или вытеснения). До индексов он совпадает с `nocache`, 3–5 запросов в секунду,
задержка до 24 с. После индексов 450–1270 запросов в секунду. В этом прогоне Redis доходит до лимита `maxmemory` (около 403 МБ) и вытесняет ключи
(`volatile-lru`, десятки и сотни тысяч вытесненных ключей на прогон): читателей в `cold` сотни тысяч, и все ленты в памяти не помещаются.
Redis при этом работает штатно (p50 остаётся в миллисекундах), вытесненные ленты пересобираются при следующем чтении.

Кэш даёт самый быстрый путь: p50 1–20 мс на всех уровнях, попаданий в кэш 96–100% (`redis-stats.csv`). Индексы на эту фазу не влияют

Узкое место записи постов теперь — CPU primary. При 100 VU p50 `POST /post/create` падает с 302–409 мс до 89 мс.

До индексов малый и средний авторы попадали в ленту за 87–194 мс, из них почти всё — поиск подписчиков перебором таблицы.
После индексов это 1–5 мс. У «знаменитости» (32 011 подписчиков, 64 страницы по 500) полный обход занимает 46–50 мс после индексов; до индексов
запрос 2 был быстрым и без индекса, поэтому разница небольшая (78–107 мс). В цифрах «последний подписчик» учитываются только подписчики, у которых
лента уже есть в Redis: остальные собираются при чтении. Поэтому задержка до подписчика без нагрузки измеряет скорость конвейера, а не пропускную способность воркера;
пропускная способность видна в разделе 6.3.

## 7. Выводы

1. Индексы `004` и `005` обоснованы замером: без них сборка ленты и fan-out читают таблицы целиком (0,7–0,8 с и 190 мс на запрос),
   с ними доли миллисекунды. Влияние на разных путях: `cold` и `nocache` быстрее в 100–500 раз, запись постов в 3–4 раза, очередь разбирается за доли секунды вместо «никогда».
2. Кэш Redis нужен и с индексами: лента из `warm` отдаётся за 1–20 мс при 2–8 тысячах запросов в секунду; сборка из БД после индексов
   держит 450–1700 запросов в секунду. 
3. Асинхронный fan-out делает цену записи независимой от числа подписчиков: пост «знаменитости» с 32 тысячами подписчиков попадает в существующие ленты за 46–50 мс,
   клиент ответа не ждёт.
4. Native и Symfony дают близкие результаты везде, кроме `warm`, где вся работа — PHP и Redis: у native 2,3–8,3 тысячи запросов в секунду, у Symfony 1,5–3 тысячи
   (разница в накладных расходах фреймворка на запрос; обе реализации Infrastructure одинаковы и проверяются `make compare-infrastructure`).
5. Лимит `maxmemory` в 384 МБ вмещает несколько тысяч лент (после прогрева 2000 читателей Redis занимал около 190 МБ). Для миллиона пользователей ленты в памяти
   не поместятся, поэтому fan-out пишет только в существующие, а остальные собираются лениво и вытесняются по `volatile-lru`.

## 8. Ограничения и допущения

- **Потеря события**: если процесс падает между фиксацией поста в PostgreSQL и `XADD`, событие теряется (outbox не вводился, решение принято сознательно). Пост остаётся в БД,
  и появится в ленте при её пересборке (после TTL, вытеснения или `/friend/delete`), но существующие ленты подписчиков его до тех пор не получат.
- **Гонка пересборки и fan-out**: пересборка ленты при промахе читает реплику (устаревание допустимо), а событие нового поста могло прийти раньше, чем репликация довезла пост:
  такой пост может на время (до следующей пересборки) отсутствовать в ленте. Backfill в воркере и `/post/get` читают с primary.
- **Redis без персистентности**: рестарт Redis сбрасывает ленты и очередь (необработанные события теряются), ленты пересобираются из БД. Для учебного ДЗ это принято.
- **Сид**: идентификаторы постов в сиде UUIDv4, у приложений UUIDv7; данные синтетические (степень дружбы и активность авторов подобраны, а не взяты из реальной сети).
- **Стенд**: 0,5 CPU на узел БД и лимиты контейнеров небольшие, абсолютные цифры зависят от машины; сравнивать нужно «до» и «после» на одном стенде. Замеры по 30 с на уровень,
  без повторов: различия в пределах нескольких процентов считать шумом.
- **`nocache` и DNS**: отказ Redis в этой фазе эмулируется сменой пароля, а не остановкой контейнера: остановленный контейнер не разрешается в DNS, и у php (`dns_opt timeout:1`)
  каждый запрос терял бы около секунды, замер показал бы таймаут DNS. Первые прогоны этой фазы были сделаны остановкой Redis и заменены.
- **Индексы до и после**: фазу `nocache` «до индексов» снимали, временно удалив индексы `004` и `005` и вернув их после; остальные фазы «до» сняты до создания индексов.
